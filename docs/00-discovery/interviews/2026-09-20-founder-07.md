# Entrevista al fundador 07 — escala, despliegue, migración y piloto

- Fecha: 2026-09-20
- Participante: fundador/equipo fundador
- Estado: **Registrada; pendiente de métricas finales y decisiones de arquitectura**
- Fuente: respuestas directas a las preguntas 113 a 142

## Respuestas normalizadas

- El piloto tendrá un comercio, dos empleados y dos cajas concurrentes.
- Volumen aproximado: 100 ventas diarias, con mayor actividad por la tarde.
- Se aceptan como objetivos preliminares menos de 0,5 segundos para agregar un artículo y menos de 30 segundos para completar una venta en efectivo.
- La caja debe poder operar las 24 horas.
- La instalación de actualizaciones será opcional; se desea reversión automática ante fallos.
- El producto será una aplicación web instalable y soportará navegadores web. La matriz de navegadores/versiones sigue pendiente.
- No hay restricciones iniciales de nube, residencia o tecnologías.
- La visión comercial pretende ofrecer opciones local, cloud e híbridas. Se acepta respaldo cifrado automático para el plan local.
- La carga inicial utilizará Excel, entrada manual o escaneo. Se desean importaciones amplias desde varios medios, sujetas a formatos reales.
- Un administrador o responsable de stock valida los datos importados.
- Configurar un comercio debería llevar entre 4 y 8 horas según tamaño, equipos y empleados.
- El plan básico no incluye capacitación humana; planes superiores incorporan servicios. El material de autoayuda debe ser lo más sencillo posible.
- El piloto será gratuito durante dos semanas.
- Requisitos declarados para participar: Internet y un dispositivo compatible.
- El equipo completo decide si una versión está lista.
- Se autoriza telemetría técnica de errores y rendimiento sin datos comerciales sensibles.
- El equipo necesita un panel interno de dispositivos, sincronización, errores, versión y respaldo.
- La política de actualizaciones dependerá del plan; se contempla incluir gratuitamente las de seguridad.
- Solicitudes e incidentes se gestionarán mediante tickets.
- Los incidentes críticos deben atenderse “a la brevedad posible”; falta un SLA medible.
- No se identificaron más integraciones imprescindibles.
- El equipo no dispone actualmente de contador o especialista fiscal.
- Prioridades declaradas: venta, caja, stock, productos, clientes/fiado, reportes y operación sin conexión.
- Facturación fiscal puede quedar fuera del primer producto, pero el comercio necesitará un mecanismo externo válido.
- Éxito: se aceptan como dimensiones comercios activos, ventas registradas, tiempo sin fallos, reducción de diferencias y satisfacción; faltan metas numéricas.

## Hallazgos y límites

- El piloto pequeño reduce riesgo y costo, pero no valida escala empresarial; esa capacidad debe preservarse mediante aislamiento y diseño evolutivo, no infraestructura sobredimensionada.
- Ofrecer local, cloud y todas las combinaciones híbridas desde el inicio multiplicaría desarrollo, pruebas, soporte, actualizaciones y migraciones. Se requiere una modalidad inicial recomendada y una evolución.
- Una aplicación web instalable con operación offline orienta a una PWA o envoltorio equivalente, pero la decisión técnica se documentará mediante ADR.
- Actualizaciones opcionales producen múltiples versiones en soporte. Las correcciones críticas de seguridad deben tener una política mínima obligatoria y comunicada, independientemente del plan comercial.
- Dos semanas pueden ser insuficientes para importar, aprender y observar cierres/fiado; la duración deberá validarse con el comercio piloto.
- “A la brevedad posible” no es verificable; se necesita tiempo de primera respuesta y restauración por severidad.
- Dejar facturación fiscal fuera no elimina obligaciones del comercio ni permite presentar un ticket interno como comprobante fiscal.
